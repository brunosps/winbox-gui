# tauri

## Targets Linux do bundler e flags de CLI
O `cargo tauri build` aceita `-b, --bundles [<BUNDLES>...]` (lista separada por espaço/vírgula) com valores Linux: `deb`, `rpm`, `appimage`; ex.: `cargo tauri build --bundles deb,appimage`. `--no-bundle` pula o empacotamento mesmo com `bundle.active=true`. Com `bundle.targets: "all"` (config atual do winbox-gui em src-tauri/tauri.conf.json) o Linux gera deb + rpm + appimage. Config específica fica em `tauri.conf.json > bundle > linux > deb` e `bundle > linux > appimage`.
[source: https://v2.tauri.app/reference/cli/ + https://v2.tauri.app/distribute/debian/ + https://v2.tauri.app/distribute/appimage/, version: Tauri 2.x docs, retrieved: 2026-07-08]

## .deb — dependências declaradas automaticamente
O .deb gerado declara automaticamente `Depends: libwebkit2gtk-4.1-0, libgtk-3-0`; se a feature `tray-icon` estiver ativa adiciona `libappindicator3-1` OU `libayatana-appindicator3-1` (detecção via pkg-config, override por env `TAURI_LINUX_AYATANA_APPINDICATOR`). Confirmado no código: tauri-cli injeta `depends_deb.push("libwebkit2gtk-4.1-0")` e `"libgtk-3-0"` em crates/tauri-cli/src/interface/rust.rs (~linhas 1443-1444). Deps extras: `bundle.linux.deb.depends` (array); arquivos extras: `bundle.linux.deb.files` (mapa destino→origem relativa ao tauri.conf.json). O .deb NÃO embute WebKit — o host resolve via apt.
[source: https://v2.tauri.app/distribute/debian/ + https://github.com/tauri-apps/tauri/blob/dev/crates/tauri-cli/src/interface/rust.rs, version: tauri-cli dev branch (compatível 2.10.x), retrieved: 2026-07-08]

## AppImage — o que é embutido
O bundler AppImage usa linuxdeploy + linuxdeploy-plugin-gtk (baixados de github.com/tauri-apps/binary-releases para ~/.cache/tauri) e o plugin GTK embute as libs GTK3/WebKitGTK; além disso o bundler copia explicitamente para o AppDir os binários `WebKitNetworkProcess`, `WebKitWebProcess` e `injected-bundle/libwebkit2gtkinjectedbundle.so` do diretório `webkit2gtk-4.1` do sistema de build (crates/tauri-bundler/src/bundle/linux/appimage/linuxdeploy.rs). Ou seja: webkit2gtk 4.1 vai DENTRO do AppImage; o host NÃO precisa dele. `bundle.linux.appimage.bundleMediaFramework: true` adiciona o plugin gstreamer (mídia; aumenta o tamanho; plugins 'ugly' têm restrição de licença). Tamanho típico: 70+ MB (vs 2-6 MB dos outros formatos). `bundle.linux.appimage.files` exige destinos começando com `/usr/`.
[source: https://v2.tauri.app/distribute/appimage/ + https://github.com/tauri-apps/tauri/blob/dev/crates/tauri-bundler/src/bundle/linux/appimage/linuxdeploy.rs, version: Tauri 2.x, retrieved: 2026-07-08]

## AppImage — runtime no Ubuntu 24.04 (FUSE)
AppImages exigem FUSE 2 em runtime; no Ubuntu 24.04 o pacote foi renomeado de `libfuse2` para `libfuse2t64` (`sudo apt-get install libfuse2t64`). Workaround sem FUSE: `./app.AppImage --appimage-extract-and-run` ou `export APPIMAGE_EXTRACT_AND_RUN=1`. O próprio bundler do Tauri usa esse mecanismo internamente ao rodar o linuxdeploy. Ubuntu 24.04 desktop NÃO traz libfuse2t64 por padrão — é fricção real de instalação para o usuário final.
[source: https://docs.appimage.org/user-guide/troubleshooting/fuse.html, version: AppImage docs atual, retrieved: 2026-07-08]

## AppImage — baseline de build (glibc) e recomendação oficial
Docs oficiais: compilar em Ubuntu 22.04 ou Debian 12 (mínimo com `libwebkit2gtk-4.1-dev` nos repositórios padrão) para não elevar o requisito de glibc — construir em sistema mais novo causa erro em host antigo: "/usr/lib/libc.so.6: version 'GLIBC_2.33' not found". Recomendação textual: "We recommend using a Docker container or GitHub Actions to build your Tauri application for Linux." Limitação: linuxdeploy não cross-compila AppImages ARM (só build nativo).
[source: https://v2.tauri.app/distribute/appimage/, version: Tauri 2.x docs, retrieved: 2026-07-08]

## Runtime Linux — problemas gráficos conhecidos (WebKitGTK)
Workarounds oficiais para tela branca/flicker/crash (sobretudo NVIDIA/Wayland), em ordem: `__NV_DISABLE_EXPLICIT_SYNC=1`, `WEBKIT_DISABLE_DMABUF_RENDERER=1`, `WEBKIT_DISABLE_COMPOSITING_MODE=1` (último recurso). Podem ser setados em código antes de criar a webview (`std::env::set_var` com `#[cfg(target_os = "linux")]`), mas a doc adverte a só embarcar override incondicional se o app for comprovadamente afetado. Adicional (não-oficial, community-reported): o AppArmor do Ubuntu 24.04 (`kernel.apparmor_restrict_unprivileged_userns=1`) bloqueia bwrap/user namespaces, o que afeta sandbox de webviews em AppImages [source: training-data + issues da comunidade, unverified para Tauri especificamente].
[source: https://v2.tauri.app/develop/debug/linux-graphics/, version: Tauri 2.x docs, retrieved: 2026-07-08]

## Updater — no Linux só AppImage; .deb não tem auto-update
O tauri-plugin-updater suporta, no Linux, SOMENTE AppImage. Com `bundle.createUpdaterArtifacts: true` o build gera `app.AppImage` + `app.AppImage.sig` (o valor legado `"v1Compatible"` gera `.AppImage.tar.gz` + `.sig` e "will be removed in v3"). Para .deb NÃO há suporte do plugin: atualização = usuário baixa/instala o .deb novo do release (ou repositório apt próprio, fora do escopo do Tauri). Config do plugin em `plugins.updater`: `pubkey` (CONTEÚDO da chave, não path), `endpoints` (aceita `{{current_version}}`, `{{target}}`, `{{arch}}`), `dangerousInsecureTransportProtocol`. Servidor estático: latest.json com `version` (SemVer), `platforms.<target>.url` e `.signature` (conteúdo do .sig), opcionais `notes` e `pub_date` (RFC 3339); alvo Linux é `linux-x86_64`. Servidor dinâmico: 200 com JSON ou 204 sem update.
[source: https://v2.tauri.app/plugin/updater/, version: tauri-plugin-updater 2.x docs, retrieved: 2026-07-08]

## Assinatura do updater (minisign)
Gerar par de chaves: `tauri signer generate -w ~/.tauri/myapp.key`. No build, exportar `TAURI_SIGNING_PRIVATE_KEY` (path OU conteúdo da chave privada) e opcionalmente `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` — a doc exige que estejam no ambiente do shell durante `tauri build` (não lê .env). O `.sig` resultante alimenta o campo `signature` do latest.json. Isso é assinatura do UPDATER (minisign), distinta de code-signing de SO — para Linux o Tauri não exige assinatura de pacote.
[source: https://v2.tauri.app/plugin/updater/, version: tauri-plugin-updater 2.x docs, retrieved: 2026-07-08]

## tauri-action (GitHub) — release, latest.json e .sig
`tauri-apps/tauri-action@v1` cria o GitHub Release e sobe os bundles Linux (.deb, .rpm, .AppImage). Inputs verificados no README: `tagName`, `releaseName`, `releaseBody`, `releaseDraft` (default false), `prerelease` (default false), `args` (flags extras pro `tauri build`, ex. `--bundles deb,appimage`), `uploadUpdaterJson` (default true — gera e sobe o latest.json quando o updater está configurado), `uploadUpdaterSignatures` (default true — sobe os arquivos .sig), `updaterJsonPreferNsis` (só Windows). Workflow de exemplo oficial: runner `ubuntu-22.04`, apt install `libwebkit2gtk-4.1-dev libappindicator3-dev librsvg2-dev patchelf xdg-utils`, env `GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}`; as env `TAURI_SIGNING_PRIVATE_KEY`/`_PASSWORD` são passadas como env do step do tauri-action via secrets.
[source: https://github.com/tauri-apps/tauri-action (README, branch dev) + https://v2.tauri.app/distribute/pipelines/github/, version: tauri-action v1, retrieved: 2026-07-08]

## Checksums SHA256 — não são gerados pelo tauri-action
Nem o bundler do Tauri nem o tauri-action geram checksums SHA256 dos artefatos (ausência verificada no README do tauri-action e nas docs de distribute — só existem os `.sig` minisign do updater). Se o release precisar de SHA256SUMS (boa prática p/ download manual do .deb/AppImage), é preciso um step próprio no workflow (ex.: `sha256sum *.deb *.AppImage > SHA256SUMS` + upload com `gh release upload`).
[source: https://github.com/tauri-apps/tauri-action README + https://v2.tauri.app/distribute/, version: tauri-action v1 / Tauri 2.x, retrieved: 2026-07-08]

## Formatos Linux oficialmente suportados
Página oficial de distribuição: "For Linux you can distribute your app using the Debian package, Snap, AppImage, Flatpak, RPM or Arch User Repository (AUR) formats." Não há ranking oficial de preferência entre formatos nem recomendação única — a escolha deb+AppImage é decisão do projeto (deb = integração apt/deps; AppImage = único formato com auto-update via plugin).
[source: https://v2.tauri.app/distribute/, version: Tauri 2.x docs, retrieved: 2026-07-08]

## summary
Pesquisa oficial (v2.tauri.app, código-fonte tauri-apps/tauri, README do tauri-action, docs.appimage.org) sobre bundler Linux do Tauri 2 para o winbox-gui (tauri 2.10.3). Resultado central: .deb e AppImage saem do mesmo `cargo tauri build` (`--bundles deb,appimage` ou `bundle.targets`); o .deb NÃO embute WebKit e declara `Depends: libwebkit2gtk-4.1-0, libgtk-3-0` automaticamente (confirmado no código do tauri-cli), enquanto o AppImage EMBUTE webkit2gtk-4.1 + GTK via linuxdeploy-plugin-gtk e cópia explícita dos processos WebKit (confirmado no código do bundler) — mas exige FUSE2 no host (libfuse2t64 no Ubuntu 24.04, não instalado por padrão; workaround --appimage-extract-and-run). Build deve ocorrer em Ubuntu 22.04/Debian 12 (baseline glibc; recomendação oficial: Docker ou GitHub Actions). Auto-update: o tauri-plugin-updater no Linux suporta SOMENTE AppImage (createUpdaterArtifacts:true gera .AppImage + .sig minisign; chave via `tauri signer generate` + env TAURI_SIGNING_PRIVATE_KEY); .deb se atualiza baixando release novo ou via repo apt próprio. tauri-action@v1 cria o release, sobe .deb/.rpm/.AppImage, gera latest.json (uploadUpdaterJson, default true) e sobe os .sig (uploadUpdaterSignatures, default true); SHA256SUMS não é gerado por nada do ecossistema Tauri — exige step manual no workflow.

## implications_for_techspec
1) Fixar `bundle.targets` explícito como `["deb", "appimage"]` no tauri.conf.json (hoje está "all", que gera também rpm sem necessidade) — ou manter "all" e usar `--bundles deb,appimage` no CI; preferir a config explícita para builds locais e CI ficarem iguais. 2) Build de release SEMPRE em Ubuntu 22.04 (container ou runner `ubuntu-22.04` do GitHub) com `libwebkit2gtk-4.1-dev libappindicator3-dev librsvg2-dev patchelf xdg-utils` — baseline glibc para o AppImage rodar em 22.04+ e 24.04. 3) Documentar requisito de runtime por artefato: .deb resolve libwebkit2gtk-4.1-0/libgtk-3-0 via apt (Ubuntu 24.04 tem nos repos padrão); AppImage não precisa de WebKit no host mas precisa de `libfuse2t64` (24.04) — o techspec deve mandar o docs/instalador avisar isso, ou orientar `--appimage-extract-and-run`. 4) Dependências do produto (docker, flatpak FreeRDP p/ WinApps) NÃO entram em `deb.depends` como hard-depends — são checadas/instaladas pelo wizard em runtime; no máximo usar `recommends`. 5) Estratégia de update: se auto-update for requisito, é só via AppImage (plugin updater + `createUpdaterArtifacts: true` + `plugins.updater.pubkey`/`endpoints` apontando pro latest.json do GitHub Release); para o .deb o techspec deve fixar "update = baixar release novo" (ou adiar repo apt). Se auto-update NÃO for requisito da v1, omitir o plugin e tratar update como release manual nos dois formatos — decisão a fixar. 6) Release pipeline: reutilizar o padrão do workflow existente (commit 60246e3) com tauri-apps/tauri-action@v1 (tagName/releaseName/releaseBody, GITHUB_TOKEN; secrets TAURI_SIGNING_PRIVATE_KEY/_PASSWORD como env do step se updater ativo) + step adicional `sha256sum` para publicar SHA256SUMS, pois nada no ecossistema Tauri gera checksums. 7) Considerar expor no app (ou docs de troubleshooting) os workarounds gráficos oficiais WEBKIT_DISABLE_DMABUF_RENDERER=1 / WEBKIT_DISABLE_COMPOSITING_MODE=1 para NVIDIA/Wayland — não embarcar incondicionalmente.

# odt

## Product ID — M365 Apps for enterprise (default recomendado)
IDs de assinatura M365 suportados pelo ODT: O365ProPlusRetail, O365BusinessRetail (mais VisioProRetail, ProjectProRetail, AccessRuntimeRetail, LanguagePack). A tabela oficial plano→ID mapeia: Office 365/Microsoft 365 E3 e E5 → O365ProPlusRetail; Microsoft 365 Business Standard e Business Premium → O365BusinessRetail; plano standalone 'Microsoft 365 Apps for enterprise' → O365ProPlusEEANoTeamsRetail; 'Microsoft 365 Apps for business' → O365BusinessEEANoTeamsRetail; variantes '(no Teams)' dos planos E3/E5 → O365ProPlusEEANoTeamsRetail. Nota oficial: 'If you use the wrong product ID, you can't activate Office' — ou seja, NÃO existe um único ID que ative para qualquer conta M365; a família ProPlus ativa com licenças enterprise e a família Business com licenças business. Para contas consumer (M365 Family/Personal) o ID é O365HomePremRetail (listado na mesma página).
[source: https://learn.microsoft.com/en-us/troubleshoot/microsoft-365-apps/office-suite-issues/product-ids-supported-office-deployment-click-to-run, version: ms.date 2025-11-07 (updated_at 2026-06-25), retrieved: 2026-07-08]

## Product ID — semântica de O365ProPlusRetail no configuration.xml
Na doc de configuração do ODT, Product ID="O365ProPlusRetail" é descrito como 'Downloads and installs Microsoft 365 Apps for enterprise'. O elemento Product é obrigatório ter o atributo ID; múltiplos Products instalam na ordem do arquivo (o primeiro define o contexto do First Run Experience).
[source: https://learn.microsoft.com/en-us/microsoft-365-apps/deploy/office-deployment-tool-configuration-options, version: ms.date 2024-12-19 (updated_at 2026-05-01), retrieved: 2026-07-08]

## Channel — Current é o default
Atributo Channel do elemento Add é opcional; se o M365 Apps NÃO está instalado no device, o default é 'Current'. Valores permitidos: BetaChannel, CurrentPreview, Current, MonthlyEnterprise, SemiAnnualPreview, SemiAnnual. O Channel do Add define o canal de instalação; o Channel do elemento Updates muda canal de instalação existente (default também Current).
[source: https://learn.microsoft.com/en-us/microsoft-365-apps/deploy/office-deployment-tool-configuration-options, version: ms.date 2024-12-19, retrieved: 2026-07-08]

## ExcludeApp — lista completa de valores permitidos
Valores permitidos do atributo ID do ExcludeApp (filhos de Product): Access, Excel, Groove, Lync, OneDrive, OneNote, Outlook, OutlookForWindows, PowerPoint, Publisher, Teams, Word. Notas oficiais: 'For OneDrive, use Groove. For Skype for Business, use Lync'; 'OutlookForWindows refers to the new Outlook app'. OneDrive é instalado automaticamente junto com Word/Excel/PowerPoint a menos que excluído. Para instalar SOMENTE Excel+Word+PowerPoint a partir de O365ProPlusRetail, excluir: Access, Groove, Lync, OneDrive, OneNote, Outlook, OutlookForWindows, Publisher, Teams (Groove E OneDrive ambos, por segurança — a doc lista os dois IDs). Sintaxe: <ExcludeApp ID="Publisher" /> dentro de <Product>. Atenção: se reaplicar config num device que já tem Office, o ExcludeApp só sobrescreve o estado anterior se a lista de Languages do XML cobrir todas as línguas instaladas; senão os ExcludeApp são COMBINADOS.
[source: https://learn.microsoft.com/en-us/microsoft-365-apps/deploy/office-deployment-tool-configuration-options, version: ms.date 2024-12-19, retrieved: 2026-07-08]

## ExcludeApp — também remove app de instalação existente
Se o M365 Apps já está instalado, rodar /configure com ExcludeApp remove o app previamente instalado (ex.: <ExcludeApp ID="Publisher" /> remove o Publisher de instalação existente). Exemplo oficial de exclusão do OneDrive: <Product ID="O365ProPlusRetail"><Language ID="en-us" /><ExcludeApp ID="OneDrive" /></Product>.
[source: https://learn.microsoft.com/en-us/microsoft-365-apps/deploy/overview-office-deployment-tool, version: ms.date 2025-05-08 (updated_at 2026-03-24), retrieved: 2026-07-08]

## Language — culture codes pt-BR e en-US
Tabela oficial de idiomas suportados: 'Portuguese (Brazil)' = pt-BR (proofing companions: Brazilian, English, Spanish); 'Portuguese (Portugal)' = pt-PT; 'English' = en-US. Sintaxe no XML (exemplos oficiais usam minúsculas): <Language ID="pt-br" /> / <Language ID="en-us" /> como filhos de <Product>. IDs especiais: MatchOS (com Fallback="en-us" recomendado + AllowCdnFallback="True"), MatchPreviousMSI, MatchInstalled (não funciona com /download).
[source: https://learn.microsoft.com/en-us/microsoft-365-apps/deploy/overview-deploying-languages-microsoft-365-apps, version: ms.date 2025-04-01, retrieved: 2026-07-08]

## Language — primeiro idioma define Shell UI; quando o idioma baixa
Se múltiplos <Language> são definidos, o PRIMEIRO do arquivo determina a Shell UI culture (atalhos, menus de contexto, tooltips); para trocar a Shell UI depois é preciso DESINSTALAR e reinstalar o M365 Apps. Download do idioma: em modo /download, todos os idiomas listados são baixados para o SourcePath; em /configure direto do CDN os idiomas são baixados durante a instalação; se instala de source local sem o language pack, o ODT usa o CDN como backup somente se AllowCdnFallback="True" (default False). Idiomas adicionais podem ser instalados depois via Product ID="LanguagePack" sobre instalação existente.
[source: https://learn.microsoft.com/en-us/microsoft-365-apps/deploy/office-deployment-tool-configuration-options, version: ms.date 2024-12-19, retrieved: 2026-07-08] e [source: https://learn.microsoft.com/en-us/microsoft-365-apps/deploy/overview-deploying-languages-microsoft-365-apps, version: ms.date 2025-04-01, retrieved: 2026-07-08]

## setup.exe — modos e sintaxe
Modos oficiais: setup.exe /download downloadconfig.xml (baixa produtos+idiomas p/ SourcePath; re-download só baixa arquivos faltantes); setup.exe /configure installconfig.xml (instala/remove/atualiza; exige admin local no guest); setup.exe /customize preferencesconfig.xml (só AppSettings em instalação existente); e modo help. ODT baixado do Microsoft Download Center (fwlink LinkID=626065 / download id=49117) — exe autoextraível com setup.exe + configuration.xml de exemplo. Em /configure, se SourcePath não é declarado, o ODT procura arquivos de instalação na MESMA pasta do setup.exe e depois usa o Office CDN; ou seja, /configure sem SourcePath instala direto do CDN (guest precisa de internet).
[source: https://learn.microsoft.com/en-us/microsoft-365-apps/deploy/overview-office-deployment-tool, version: ms.date 2025-05-08, retrieved: 2026-07-08] e [source: https://learn.microsoft.com/en-us/microsoft-365-apps/deploy/office-deployment-tool-configuration-options (SourcePath attribute), version: ms.date 2024-12-19, retrieved: 2026-07-08]

## Tamanhos de download
Números oficiais (doc dos Microsoft 365 Apps Rangers): source files completos do M365 Apps ≈ 3 GB por arquitetura+1 idioma ('source files (of ~3 gigabytes)'; pacote lean = 'from 3 GB down to less than 10 megabytes for the ODT and its configuration file'). Language pack completo adicional: 200–300 MB; proofing tools: 30–50 MB; Project 2nd-install: <50 MB; Visio: 100–200 MB. NÃO há número oficial do download líquido quando ExcludeApp remove apps — o stream.x64 é o grosso do pacote e é language-neutral/suite-wide; assumir ~3 GB mesmo excluindo apps [source: training-data, unverified para esta última inferência].
[source: https://learn.microsoft.com/en-us/microsoft-365-apps/best-practices/build-dynamic-lean-universal-packages, version: ms.date 2024-05-25, retrieved: 2026-07-08]

## Display Level None + AcceptEULA
Sintaxe: <Display Level="None" AcceptEULA="TRUE" /> (elemento top-level de Configuration). Level opcional, default 'Full'; com 'None' instala sem NENHUMA UI (sem progress bar, telas de conclusão ou mensagens de erro). AcceptEULA opcional, default 'FALSE'; com TRUE o usuário não vê o diálogo de Microsoft Software License Terms — Microsoft recomenda admins setarem TRUE. Para instalação 100% não-assistida ambos são obrigatórios no nosso caso.
[source: https://learn.microsoft.com/en-us/microsoft-365-apps/deploy/office-deployment-tool-configuration-options, version: ms.date 2024-12-19, retrieved: 2026-07-08]

## OfficeClientEdition — 64-bit
Atributo opcional do Add; valores '64' ou '32'. Se Office não instalado e atributo ausente, ODT auto-seleciona 64-bit (32-bit só se Windows 32-bit ou <4 GB RAM). Se já instalado e o valor especificado não bate com a arquitetura existente, a instalação FALHA (mixed archs não suportadas). Fixar OfficeClientEdition="64" explicitamente é seguro no nosso guest Win11 x64 e coerente com os paths x64 do WinApps.
[source: https://learn.microsoft.com/en-us/microsoft-365-apps/deploy/office-deployment-tool-configuration-options, version: ms.date 2024-12-19, retrieved: 2026-07-08]

## Verificação de sucesso — sinais oficiais
Sinais documentados: (a) ao fim do /configure o prompt exibe 'Products configured successfully.'; (b) logs de troubleshooting ficam em %temp% (arquivos de log do ODT/C2R). A Microsoft NÃO publica uma tabela oficial de exit codes do setup.exe do ODT nas docs de deploy; a convenção de detecção (usada pelo Intune Win32) é exit code 0 = sucesso do instalador, mas Microsoft recomenda detecção pós-install por regra (registry/arquivo), não confiar só no exit code [source: https://learn.microsoft.com/en-us/intune/app-management/deployment/add-win32 + training-data para a ausência de tabela oficial, parcialmente unverified].
[source: https://learn.microsoft.com/en-us/microsoft-365-apps/deploy/overview-office-deployment-tool, version: ms.date 2025-05-08, retrieved: 2026-07-08]

## Verificação de sucesso — registry keys Click-to-Run
Chave canônica de detecção: HKLM\SOFTWARE\Microsoft\Office\ClickToRun\Configuration com valores ProductReleaseIds (ex.: 'O365ProPlusRetail'), VersionToReport (ex.: '16.0.xxxxx.yyyyy'), Platform ('x64') e UpdateChannel — confirmada em respostas Microsoft Q&A e blog técnico arquivado da Microsoft, mas não em página de docs formal. Alternativa usada como detection rule: HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall\O365ProPlusRetail - pt-br (DisplayName) — o sufixo é o idioma primário instalado [source: training-data + Microsoft Q&A, semi-verified].
[source: https://learn.microsoft.com/en-us/archive/blogs/jensha/click2run-installationen-erkennen (blog MS arquivado) e https://learn.microsoft.com/en-us/answers/questions/438018/, version: arquivo/Q&A sem ms.date formal, retrieved: 2026-07-08]

## Verificação de sucesso — paths dos .exe x64
Instalações Click-to-Run 64-bit colocam os executáveis em C:\Program Files\Microsoft Office\root\Office16\: EXCEL.EXE, WINWORD.EXE, POWERPNT.EXE (pasta 'root' é exclusiva do C2R; 'Office16' é a família 16.0 usada por M365 Apps/2019/2021/2024). Confirmado em múltiplas threads Microsoft Q&A (learn.microsoft.com/answers), não em página de docs formal — e coincide com os paths que as defs de apps do WinApps upstream esperam. Checagem programática recomendada: existência dos 3 .exe + registry ClickToRun\Configuration.
[source: https://learn.microsoft.com/en-us/answers/questions/5090991/ e https://learn.microsoft.com/en-us/answers/questions/4890162/, version: Microsoft Q&A (semi-oficial), retrieved: 2026-07-08]

## Gotcha — /download vs config lean
Configs 'lean' com Version="MatchInstalled"/Language MatchInstalled só funcionam com /configure, NÃO com /download (ODT não tem detalhes p/ download, ex. arquitetura). Ao usar /download num folder que já tem a mesma versão, o ODT baixa só arquivos faltantes (ex.: adicionar 2º idioma baixa só o language pack). DownloadPath exige Version explícito. Network connectivity é exigida em modo download mesmo com DownloadPath local.
[source: https://learn.microsoft.com/en-us/microsoft-365-apps/best-practices/build-dynamic-lean-universal-packages, version: ms.date 2024-05-25, retrieved: 2026-07-08] e [source: https://learn.microsoft.com/en-us/microsoft-365-apps/deploy/office-deployment-tool-configuration-options, version: ms.date 2024-12-19, retrieved: 2026-07-08]

## 3. Mecânica de detecção de apps (scan via RDP)
Detecção em 2 estágios, executada DENTRO do Windows via sessão RemoteApp do FreeRDP (`/app:program:"C:\Windows\System32\cmd.exe",cmd:"/C <installed.bat>"`), com scripts trafegando pelo share +home-drive (\\tsclient\home\.local\share\winapps\): (1) waFindInstalled gera ~/.local/share/winapps/installed.bat com uma linha `IF EXIST "<WIN_EXECUTABLE>" ECHO <app>^|^|^|<WIN_EXECUTABLE>` por app oficial — só apps cujo executável EXISTE no Windows entram na lista; (2) o batch chama `powershell.exe -ExecutionPolicy Bypass -File ExtractPrograms.ps1 > detected` para extrair nome/caminho/ícone-base64 dos demais .exe do Registry do Windows, e finaliza com `tsdiscon`. # dockur

## /oem — como a pasta entra no Windows
No v5.14, a função addFolder() (define.sh) procura a pasta na ordem /oem → /OEM → $STORAGE/oem → $STORAGE/OEM e copia com `cp -Lr` para `$OEM$/$1/OEM` dentro da ISO de instalação (mecanismo $OEM$ do Windows Setup copia para C:\OEM, pois $1 = %SystemDrive%). A cópia acontece NO MOMENTO DO BUILD DA ISO (install.sh, msg 'Adding OEM folder to image...'), ou seja, só na instalação inicial — mudar /oem depois do disco instalado não tem efeito. Só o install.bat de primeiro nível (find -maxdepth 1 -iname install.bat) recebe unix2dos (CRLF); demais .bat/.ps1 mantêm line endings originais — gotcha se o winbox gerar scripts auxiliares com LF.
[source: https://raw.githubusercontent.com/dockur/windows/v5.14/src/define.sh (addFolder) e https://raw.githubusercontent.com/dockur/windows/v5.14/src/install.sh, version: v5.14, retrieved: 2026-07-08]

## /oem — quando e como install.bat roda
No win11x64.xml do v5.14, o install.bat é o ÚLTIMO FirstLogonCommand (pass oobeSystem, Order 26): `cmd /C if exist "C:\OEM\install.bat" start "Install" "cmd /C C:\OEM\install.bat"`. Roda no PRIMEIRO LOGON da conta de auto-logon (AutoLogon Username=Docker, LogonCount=65432 — substituída pelo USERNAME/PASSWORD do env), NÃO como SYSTEM. O `start` lança o script destacado numa janela cmd visível na sessão interativa — o setup não espera ele terminar. Orders 1-2 (antes dele) habilitam AllowInsecureGuestAuth e desligam SMB signing, então \\host.lan\Data já é acessível quando o install.bat roda.
[source: https://raw.githubusercontent.com/dockur/windows/v5.14/assets/win11x64.xml, version: v5.14, retrieved: 2026-07-08]

## /oem — contexto de privilégio (doc oficial Microsoft)
FirstLogonCommands rodam uma única vez, 'after logon, prior to showing the desktop'; quando o usuário que loga tem privilégio administrativo, 'these commands are run with elevated access privileges' (a conta do dockur é admin → install.bat roda elevado). ATENÇÃO: no Windows atual 'all commands using these unattend settings are now started at the same time, and no longer wait for the previous command to finish' (comportam-se como AsynchronousCommand) — o install.bat não pode assumir que os reg.exe anteriores já terminaram; deve fazer os próprios waits/retries (ex.: esperar rede antes de chamar o ODT).
[source: https://learn.microsoft.com/en-us/windows-hardware/customize/desktop/unattend/microsoft-windows-shell-setup-firstlogoncommands, version: doc 2018-04-04 (vigente), retrieved: 2026-07-08]

## /oem — limitações e issues conhecidos (#677, #1104, #1031)
Issue #677: install.bat montado via symlink (K8s ConfigMap) era descartado pelo genisoimage ('Symlink ... ignored - continuing' no log do container) → aparecia como diretório vazio no guest; o v5.14 usa `cp -Lr` (deref de symlinks) na cópia, mas o log do genisoimage continua sendo o sinal de diagnóstico. ## /oem — como debugar se não rodou
Checklist de debug: (1) log do container deve ter 'Adding OEM folder to image...' — ausente = pasta não detectada (nome/mount errado); (2) warnings 'genisoimage: Symlink ... ignored' = arquivos caíram fora da ISO; (3) no guest, verificar se C:\OEM existe com o install.bat dentro (se existe mas não rodou, é o caso #1104 — rodar manualmente funciona, e os logs do unattend ficam em C:\Windows\Panther\); (4) disco já instalado (data.img existente) = ISO não é reconstruída = install.bat nunca roda de novo; (5) MANUAL=Y = nunca roda.

## MANUAL e ARGUMENTS — semântica exata
MANUAL: "Y" = 'perform the installation manually at your own risk' — desliga a instalação automática/unattend inteira; incompatível com o perfil Office (install.bat não roda, RDP/autologon/tweaks não são configurados). ARGUMENTS = argumentos extras passados direto ao QEMU (ex. oficial: `-device usb-host,vendorid=0x1234,productid=0x1234` + devices /dev/bus/usb) — útil no futuro p/ passthrough, desnecessário para Office. Nenhuma env var dockur controla 'esperar install.bat terminar' — a detecção de conclusão do provisionamento é responsabilidade do orquestrador (winbox).
[source: https://raw.githubusercontent.com/dockur/windows/v5.14/readme.md (seções 'How do I perform a manual installation?' e 'How do I pass-through a USB device?'), version: v5.14, retrieved: 2026-07-08]

## FreeRDP flatpak — invocação
Invocação canônica (usada na doc do WinApps): `flatpak run --command=xfreerdp com.freerdp.FreeRDP /u:... /p:... /v:127.0.0.1:3389 /cert:tofu`. O `--command=xfreerdp` é obrigatório porque o command default do manifest é `sdl-freerdp` (cliente SDL3; o manifest builda com WITH_CLIENT_SDL3=ON). O próprio bin/winapps usa como fallback exatamente `flatpak run --command=xfreerdp com.freerdp.FreeRDP` quando não há xfreerdp/xfreerdp3 nativo.
[source: https://github.com/winapps-org/winapps/blob/main/README.md (Step 4: Test FreeRDP) + https://raw.githubusercontent.com/flathub/com.freerdp.FreeRDP/master/com.freerdp.FreeRDP.json (command: sdl-freerdp), version: main/master 2026-07, retrieved: 2026-07-08]

## FreeRDP flatpak — detecção programática de instalação e versão
Existência: `flatpak info com.freerdp.FreeRDP` retorna exit 0 se instalado, exit 1 se não (verificado localmente na máquina alvo, Flatpak 1.14.6). NÃO parsear a saída humana do `flatpak info` — ela é LOCALIZADA (pt-BR imprime 'Versão:'). Versão machine-readable: `flatpak list --app --columns=application,version` (tab-separated; é o método que o setup.sh do WinApps usa: `flatpak list --columns=application | grep -q '^com.freerdp.FreeRDP$'` + extração da coluna version). Gotcha real: a versão atual no Flathub reporta a string `3.28.` (com ponto final, typo no appdata.xml do Flathub) — o parser de versão deve ser tolerante (extrair major com regex, exigir >= 3 como o WinApps: `((FREERDP_MAJOR_VERSION >= 3))`). Permissões efetivas (base+overrides): `flatpak info --show-permissions com.freerdp.FreeRDP`; só overrides: `flatpak override --show com.freerdp.FreeRDP`.
[source: https://raw.githubusercontent.com/winapps-org/winapps/main/setup.sh + https://raw.githubusercontent.com/flathub/com.freerdp.FreeRDP/master/com.freerdp.FreeRDP.appdata.xml (release 3.28. de 2026-07-06) + verificação local flatpak 1.14.6 em 2026-07-08, version: WinApps main / Flathub 3.28, retrieved: 2026-07-08]

## FreeRDP flatpak — permissões default do sandbox (manifest atual, FreeRDP 3.28)
finish-args oficiais do manifest Flathub: `--share=network` (rede LIBERADA por default — RDP p/ 127.0.0.1:3389 funciona sem override), `--share=ipc`, sockets x11/wayland/pulseaudio/cups/pcsc, `--device=dri`, e filesystem APENAS `--filesystem=xdg-download`. NÃO há acesso ao home por default, nem na 3.27+/3.28 — o override `flatpak override --filesystem=home com.freerdp.FreeRDP` CONTINUA necessário para o `+home-drive` expor o home real (sem ele, o drive redirecionado mostra só a visão vazia/parcial do sandbox). O README do WinApps mantém essa instrução como passo obrigatório do caminho flatpak. Forma sem root: `flatpak override --user --filesystem=home com.freerdp.FreeRDP`. Na máquina do usuário o override `filesystems=home` já está aplicado (confirmado via flatpak override --show). Runtime: org.freedesktop.Platform 25.08; build com WITH_FUSE=OFF (transferência de arquivos via clipboard/FUSE desabilitada no flatpak) e WITH_CUPS=ON.
[source: https://raw.githubusercontent.com/flathub/com.freerdp.FreeRDP/master/com.freerdp.FreeRDP.json (finish-args) + https://github.com/winapps-org/winapps/blob/main/README.md ('run the following command once to allow the use of +home-drive: sudo flatpak override --filesystem=home com.freerdp.FreeRDP'), version: Flathub FreeRDP 3.28.0 / WinApps main, retrieved: 2026-07-08]

## RDP_FLAGS — default do WinApps e como é consumido
Template oficial do winapps.conf no README: `RDP_FLAGS="/cert:tofu /sound /microphone +home-drive"` (DEFAULT VALUE documentado). Também existem `RDP_FLAGS_NON_WINDOWS` e `RDP_FLAGS_WINDOWS` (defaults vazios) para flags específicas por tipo de sessão. O bin/winapps simplesmente concatena: `FREERDP_COMMAND="${FREERDP_COMMAND} ${RDP_FLAGS}"` antes dos args fixos (/d:, /u:, /scale:, +auto-reconnect, /wm-class:, /app:program:...). Outras chaves: WAFLAVOR aceita 'docker'|'podman'|'libvirt'|'manual'; RDP_IP default 127.0.0.1 p/ docker; RDP_PORT 3389; FREERDP_COMMAND permite forçar o comando (ex. o wrapper flatpak). Sugestões documentadas de flags extras: /multimon, /kbd:unicode, /network:lan, /prevent-session-lock 120.
[source: https://github.com/winapps-org/winapps/blob/main/README.md (template winapps.conf, linhas RDP_FLAGS) + https://raw.githubusercontent.com/winapps-org/winapps/main/bin/winapps, version: main 2026-07, retrieved: 2026-07-08]

## Sintaxe FreeRDP 3.x — /cert:ignore e +home-drive confirmados no source
No cmdline.h do FreeRDP 3.28: opção `cert` com valores `[deny,ignore,name:<name>,tofu,fingerprint:<hash>:<hex>...]` → `/cert:ignore` é sintaxe válida 3.x (ignora verificação sempre; `/cert:tofu` aceita e pina no primeiro uso — é o default do WinApps). Opção `home-drive` é COMMAND_LINE_VALUE_BOOL default false, descrição oficial: 'Redirect user home as share' → habilita com `+home-drive`, que redireciona o $HOME do cliente como drive dentro da sessão RDP (aparece como \\tsclient\home / drive no Explorer do guest — é por onde o Excel abre os .xlsx do Linux). Sob flatpak, o xfreerdp só enxerga o filesystem que o sandbox concede — daí a dependência do override --filesystem=home.
[source: https://github.com/FreeRDP/FreeRDP/blob/master/client/common/cmdline.h (linhas 97-99 'cert' e 265-266 'home-drive'), version: FreeRDP 3.28.0, retrieved: 2026-07-08]

## /shared como canal runtime vs /oem como canal install-time
Diferença operacional chave: /oem é congelado na ISO no primeiro boot (imutável depois); /shared é um share Samba vivo ('Data' → \\host.lan\Data, symlink 'Shared' no Desktop criado pelo FirstLogonCommand `cmd /C mklink /d %userprofile%\Desktop\Shared \\host.lan\Data`) que reflete o host em tempo real. Para o perfil Office: configuration.xml do ODT + bootstrap pequeno vão no /oem; payloads grandes ou atualizáveis (OfficeSetup.exe, layout offline do ODT se optar por pré-download) podem ir no /shared e ser referenciados pelo install.bat via \\host.lan\Data — sem rebuild de ISO.
[source: https://raw.githubusercontent.com/dockur/windows/v5.14/src/samba.sh + https://raw.githubusercontent.com/dockur/windows/v5.14/assets/win11x64.xml (mklink Shared), version: v5.14, retrieved: 2026-07-08]

## implications_for_techspec
O techspec deve fixar: (1) VERSION="11" (Win11 Pro) pinado com dockurr/windows:5.14; NUNCA setar MANUAL; não usar DHCP/macvlan — o NAT default já dá internet ao guest para o ODT baixar do CDN. C:\OEM\provision-done.txt ou arquivo no \\\\host.lan\\Data para o winbox ler do lado Linux via a pasta /shared), (c) loga em arquivo (C:\OEM\provision.log); o wizard do winbox monitora o marker com timeout e oferece diagnóstico guiado (checar 'Adding OEM folder to image...' no docker logs, warnings de symlink do genisoimage, existência de C:\OEM no guest) + fallback 'executar C:\OEM\install.bat manualmente'. Scripts auxiliares gerados pelo winbox devem ser escritos com CRLF (só o install.bat top-level recebe unix2dos). (5) setup-host DEVE manter o override `flatpak override --filesystem=home com.freerdp.FreeRDP` (preferir a variante --user para não exigir root) — o manifest 3.28 ainda concede só xdg-download; validar pós-setup com `flatpak info --show-permissions | grep home`.
